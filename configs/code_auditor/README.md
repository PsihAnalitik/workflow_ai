# Цех `code_auditor`

Статический аудит исходного кода на уязвимости (раздел 3 ТЗ
`materials/security_shops_task_statement.md`). Вход — файл исходника,
выход — `vuln_report` на элемент.

## Состязательная структура (FR-C1)

```
hypothesis  →  refutation  →  judge[review]
```

| Узел | Что делает | Что ему ЗАПРЕЩЕНО |
|---|---|---|
| `hypothesis` | карта точек входа и опасных вызовов, ≥5 независимых гипотез с путём достижимости | решать, реальна ли уязвимость |
| `refutation` | по каждой гипотезе — основание A–E со ссылкой «файл:строка» | выдвигать новые гипотезы |
| `judge` | вес по таблице достижимости, добавление несопоставленных срабатываний сканеров, вердикт | исправлять код |

Одностадийный аудит запрещён ТЗ: он даёт неотличимый от шума поток гипотез.

Узел с одним предшественником видит ТОЛЬКО его артефакт, поэтому исходник
доступен всем трём узлам через `material_get` (`inline_limit_chars: 0`).
Побочный выигрыш: код с литеральными двойными скобками не роняет сборку
промпта. Плата: `refutation` обязан переносить поля гипотезы дословно —
`judge` исходных гипотез не видит.

## Внешний оракул (FR-C2)

`tools/prepare_code_items.py` гоняет `bandit` и `semgrep` через
`workshop/sandbox.py` (M-10) в контейнере `workshop-audit:latest`
с `--network none` и подшивает сжатый вывод в элемент секцией `<scanners>`.
Анализируемый код не исполняется (NFR-C2).

```bash
docker build -t workshop-audit:latest configs/code_auditor/docker

.venv/bin/python configs/code_auditor/tools/prepare_code_items.py \
    --files 'configs/code_auditor/stand/vulnerable/*.py' \
    --out projects/code_auditor/items --prefix vuln_

.venv/bin/python -m workshop map code_auditor \
    --files 'projects/code_auditor/items/*.md' --workers 2
```

Набор правил `semgrep` локальный (`tools/semgrep_rules.yml`): `--config auto`
требует обращения к реестру правил, а сканеры гоняются без сети. Набор
минимальный — это точка отсчёта, а не полноценный анализатор.

ЕСЛИ docker или образ недоступны — элемент собирается, а в `<scanners>`
пишется причина. Молчаливого «сканеры чисты» быть не должно: цех обязан
превзойти baseline сканеров, и подмена их вывода пустотой превратила бы
сравнение в фикцию.

## Правило достижимости (FR-C3)

Вес назначается по таблице из `wiki/security/reachability.md`, а не по классу
уязвимости: находка без выписанного пути от недоверенного входа либо с
основанием опровержения A–D уходит в 🟢p3 и остаётся в отчёте. Удалённая
находка теряется, понижённая — проверяема при следующем прогоне.

Шкала весов — как в ТЗ: `p0` высший (блокирует), `p3` низший. Она обратна
остальным цехам фабрики и объявлена в графе: `"severity_scale": "p0_high"`.

## Стенд

`stand/vulnerable/report_service.py` и `stand/fixed/report_service.py` — пара
«до/после» с разметкой в `stand/labels.jsonl`. Кроме двух настоящих
уязвимостей (CWE-89, CWE-22) файл содержит три приманки: `subprocess`
списком без `shell=True`, `md5` как ключ кэша, `eval` в мёртвом коде.

Результат дымового прогона (deepseek-v4-pro, temperature=0):

| | уязвимая | исправленная |
|---|---|---|
| CWE-89 (SQL-инъекция) | 🔴p0, путь выписан, ground E | 🟢p3, ground B (параметризация) |
| CWE-22 (выход за каталог) | 🔴p0, путь выписан, ground E | 🟢p3, ground B (`is_relative_to`) |
| приманки (3) | 🟢p3, основания B/B/C | 🟢p3 |
| шум сканеров | 🟢p3, ground A/C | 🟢p3, ground C |
| вердикт | NOT_READY | READY |

Сканеры на исправленном файле дали 4 срабатывания (`eval`, `subprocess`),
цех понизил их до p3 со ссылкой на строку — это и есть добавка к статическому
анализатору: ни одной ложной находки p0 на исправленной версии (AC-C3 на
этой паре выполнен).

## Чего в цехе НЕТ

- **Корпуса пар CVE (AC-C1) и измеренного baseline `semgrep` (AC-C4).**
  Стенд из одной пары годится для отладки, но вердиктом о качестве цеха
  не является. Метрики AC-C2/AC-C3 не измерялись.
- **Привязки к `threat_model` (FR-C5)** — узел ставит
  `threat="вне_модели_угроз"`, пока артефакта модели угроз нет в цепочке.
- **`pip-audit`** установлен в образе, но не вызывается: он проверяет
  зависимости, а элемент цеха — отдельный файл.
