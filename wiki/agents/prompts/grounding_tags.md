# wiki: инженерная проверка фабрикации — протокол found_data (v1)

Паттерн value-level grounding для LLM-ассистентов данных (снят с боевого контура
стороннего проекта, ALG-04/D2–D3): промпт-правила против фабрикации — вероятностная
защита; протокол делает её ПРОВЕРЯЕМОЙ кодом. Подаётся roast-узлам вместе с
[review.md](review.md): промпты и код сборки, несущие данные, проверяются на этот контур.

## Механизм

Модель обязана инкапсулировать каждое сообщаемое значение в inline-тег в месте
употребления; детерминированный код сверяет содержимое тегов с наблюдениями
инструментов текущего хода. Что не размечено — не считается данными; что размечено,
но не наблюдалось — фабрикация.

- **Разметка**: `<found_data>значение</found_data>` вокруг каждого значения/факта;
  отсутствие данных — ТОЛЬКО вложенным `<no_data>…</no_data>`; пустой маркер
  `<found_data><no_data/></found_data>` обязателен даже в бес-данном ответе
  (small talk) — отсутствие маркера само по себе отличимо от «данных нет».
- **Source-теги** (смешанный ход): внутри `found_data` вложенный тег с именем
  инструмента (`<query_database>236</query_database>`, `<news_smi>факт</news_smi>`) —
  числовая сверка применяется ТОЛЬКО к data-value источникам; числа в новостном
  тексте (даты, счётчики) показателями не считаются.
- **Гейты (код, не LLM)**: (а) маркер присутствует; (б) числа из data-value тегов
  найдены в наблюдениях дословно (после нормализации разрядных разделителей);
  (в) presence-логика по КОМПОЗИЦИИ наблюдений: непустой результат ⇒ непустой
  found_data, пустые наблюдения ⇒ непустой found_data = фабрикация. Ход считается
  data-ходом по СОДЕРЖАТЕЛЬНОМУ результату data-инструмента, не по факту вызова.
- **Эскалация**: провал гейта → reground (возврат модели с адресным nudge по
  конкретному провалу), лимит N циклов → детерминированный исход кодом: подмешка
  данных дословно из наблюдений (фабрикация не доставляется) либо подавление.
- **Рендер**: перед выдачей пользователю теги снимаются; проза остаётся единственной
  презентацией — дубль «текст + отдельный блок данных» невозможен по построению.

## Правило четырёх точек синхронизации

Протокол живёт одновременно в: (1) промпт-зоне (правила + примеры), (2) парсере
тегов, (3) детерминированных гейтах, (4) рендере. Изменение любой точки без
остальных — дефект p3: например, пример в гейтированной guidance-зоне БЕЗ разметки
глушит протокол у модели (семантическая интерференция), хотя основная зона
разметку требует.

## Что проверять при прожарке (промпта или кода сборки)

- ЕСЛИ промпт сообщает пользователю значения/факты из инструментов → в нём есть
  зона протокола разметки И ВСЕ примеры-эталоны ответа несут разметку (включая
  «данных нет» и small talk). Пример без разметки в любой подставляемой зоне — находка.
- ЕСЛИ промпт-зона обещает поведение («каждое значение сверяется») → в коде есть
  соответствующий гейт; ЕСЛИ гейт требует разметку → зона и примеры её показывают
  (двусторонняя проверка точки 1 ↔ точка 3).
- ЕСЛИ негативный пример содержит правдоподобные конкретные числа в always-on зоне →
  риск эха значений в ответ; негативные примеры с числами — только в гейтированных
  зонах или без реалистичных величин.
- НЕ находка: протокол отсутствует в промпте, который данных пользователю не сообщает
  (роутер, классификатор, внутренний план).
