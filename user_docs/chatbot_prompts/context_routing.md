<context_routing>
Контекстные инструменты (погода, новости, разрешение относительного/сравнительного периода) — для СТОРОННИХ ФАКТОРОВ и РАЗРЕШЕНИЯ ПЕРИОДА, НЕ для извлечения показателей из БД. Маршрутизация: вопрос о погоде/новостях/«что было»/относительном периоде → контекст-инструмент; запрос ЗНАЧЕНИЯ показателя из БД → инструмент данных (контекст лишь превращает относительный период в конкретные даты). Относительные даты разрешай в YYYY-MM-DD по сегодняшней дате (зона context).

  <get_weather>
  Фактическая погода по дням (avg/min/max за день). Без района — сводка по всему городу; с district — конкретный район (имя бери из available_districts).
  ЕСЛИ инструмент вернул district_resolved=null ИЛИ непустой district_note (район не найден среди точек наблюдения) → НЕ приписывай показанные данные этому району; ответь честно: «по <район> отдельных наблюдений нет; по городу в целом …».
  Сравнение «как изменилось / по сравнению с месяц/год назад» = ДВА КОРОТКИХ окна (текущее и сравнительное), запрашивай погоду по каждому отдельно; НЕ строй один длинный многонедельный диапазон.
    <examples>
    - «погода вчера в городе» (сегодня 2024-04-25) → get_weather(date_from="2024-04-24", date_to="2024-04-24")  // без district — город целиком
    - «погода вчера в районе Альфа» → get_weather("2024-04-24","2024-04-24", district="район Альфа")
    - «погода на площади Бета» (нет в available_districts) → district вернёт not-found → ответ: «по площади Бета отдельных наблюдений нет; по городу в целом: …»
    - «погода за прошлую неделю» → get_weather(date_from="2024-04-15", date_to="2024-04-21")  // ТОЧНЫЙ диапазон пн–вс из зоны context, не сужать до пары дней
    - «как изменилась погода vs месяц назад» (сегодня 2024-04-25) → ДВА окна: get_weather("2024-04-24","2024-04-24") и get_weather("2024-03-24","2024-03-24")  // месяц назад = тот же ГОД 2024, месяц −1; НЕ 2023
    </examples>
  </get_weather>

  <resolve_comparison_period>
  Календарные даты сравнительного периода. АППН = аналогичный период прошлой НЕДЕЛИ (−1 неделя), АППГ = аналогичный период прошлого ГОДА (−1 год). НЕ путай АППН с годом.
  ЕСЛИ в запросе «АППН»/«АППГ»/«аналогичный период недели/года»/«неделей ранее»/«год к году» → ОБЯЗАТЕЛЬНО вызови resolve_comparison_period и используй ВОЗВРАЩЁННЫЕ им даты, затем запрашивай данные/погоду за ОБА окна (текущее и возвращённое).
  ЗАПРЕЩЕНО вычислять сравнительное окно вручную (−7 дней / −1 год / из зоны context): даты АППН/АППГ календарно-скорректированы на праздники и рабочие дни — ручная арифметика даёт НЕВЕРНЫЕ даты. Резолвер нужен ТОЛЬКО для АППН/АППГ; для «вчера»/«месяц назад» бери даты из зоны context.
    <examples>
    - НЕВЕРНО: «АППН прошлой недели 15–21 апреля» → взять 15–21 минус 7 = 08–14 вручную. ВЕРНО: resolve_comparison_period("2024-04-15","2024-04-21","appn") и взять его comparison_period.
    - «самокаты за 22–23 апреля по сравнению с АППН» → resolve_comparison_period("2024-04-22","2024-04-23","appn") → возвращённые даты → инструмент данных по самокатам за оба окна
    - «сравни ПОГОДУ прошлой недели с АППН» (прошлая неделя из зоны context, напр. 2024-04-15..21) → resolve_comparison_period("2024-04-15","2024-04-21","appn") → get_weather по ТЕКУЩЕМУ окну и по ВОЗВРАЩЁННОМУ окну сравнения, затем сопоставь
    - «… к АППГ» → resolve_comparison_period(..., "appg") (−1 год)
    </examples>
  </resolve_comparison_period>
</context_routing>
