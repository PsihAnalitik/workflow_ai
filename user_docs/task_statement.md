# Постановка задачи: «Агентская мастерская»

Фреймворк агентной разработки ПО по артефактной методологии (GRACE-подобной):
конвейер мастерских-агентов с контекстной изоляцией, управляемый FSM-оркестратором,
с обязательными точками ревью (агентского и человеческого) между этапами.

Статус: v6 — v5 (v4 + CLI фабрики FR-22) дополнена MCP-интеграцией: §7.6
(FR-23), решение §10 №15 (автор, 09.07.2026; ТЗ — НА ПРИЁМКЕ автора).
История: v4 = цех актуализации wiki FR-21; v3 = wiki-база знаний
(§7.5 FR-18..FR-20).
База: v2 сведена из материалов `user_docs/`, `prompts/`, `text_searcher/`;
открытые вопросы закрыты решениями автора 08.07.2026 (см. §10).

---

## 1. Проблема

Существующие AI-инструменты кодинга (Claude Code, Codex, Cursor) дают только
«рекомендательные» механизмы кастомизации (skills, hooks, system instructions):

- нельзя **декларативно** ограничить, какой контекст и какие инструменты доступны
  агенту на конкретном этапе разработки — всё сваливается в один общий контекст;
- нет управляемых переходов между этапами: проверки методологии приходится
  хардкодить, гейты «этап не пройден — дальше нельзя» не выражаются штатно;
- нет инструмента оптимизации стоимости: выбор модели под когнитивную сложность
  этапа (дешёвая модель на проекцию, дорогая на проектирование) не поддержан;
- автономный пайплайн «требования → архитектура → код → тесты → приёмка»
  собирается только вручную и не переиспользуется между проектами.

Следствие: LLM генерирует код из размытого belief state — без трассируемости
к требованиям, с контекстным шумом от нерелевантных этапу материалов.

## 2. Идея решения (одним абзацем)

Разработка представляется как **граф состояний**, каждый узел которого —
**мастерская**: инкапсулированный агент, которому подаётся *только* релевантная
этапу информация (промпт, wiki, шаблоны, few-shot примеры, инструменты) и который
производит ровно один **артефакт** с трассировкой к старшим артефактам.
Между узлами — **единый интерфейс обмена** (версионированные артефакты со
стабильными id). В любую точку графа **инъектируются** узлы ревью: агентского
(чек-лист правил + вердикт-гейт) и человеческого (accept / правки / reject
на новый цикл). Оркестратор — **finite state machine**, который управляет
переходами и контролирует готовность этапов.

### 2.1. Канонический пайплайн артефактов

```
requirements → domains → contracts → openapi → architecture / developmentplan (C4)
```

Принцип: проектировать **поэтапно**, разделяя бизнес-логику, архитектуру и
технологический стек реализации (в исходном GRACE эти слои смешаны — поэтому
GRACE-этапы вливаются в этот пайплайн, а не наоборот):

- `requirements` — бизнес-слой: ФТ/НФТ, тех-агностично (TECH_MODE=STRICT);
- `domains`, `contracts` — логическая архитектура: границы, контракты, IO — тоже STRICT;
- `openapi` — протокол-проекция контрактов (TECH_MODE=PROJECTION);
- `architecture / developmentplan (C4)` — контейнеры, техстек, алгоритмы
  реализации, план работ — вход мастерской кодогенерации.

### 2.2. Подготовительный этап: проектирование шаблонов артефактов и wiki

Перед запуском основного пайплайна цех комплектуется рабочими материалами —
это отдельный этап со своей мастерской и своим ревью:

- **шаблоны артефактов**: XML/HTML-скелеты артефактов каждой стадии, id-схемы,
  правила кросс-ссылок; stage-карты (`@fragment`) под каждую мастерскую цеха;
- **wiki**: подборки документации по библиотекам техстека, шаблоны реализации,
  few-shot примеры хорошего и плохого использования (positive/negative) —
  ровно те материалы, которые потом контекстно изолированно подаются на узлы;
- выход этапа складывается в `wiki/` и переиспользуется между проектами цеха;
  golden-пример `text_searcher/` — первый источник наполнения.

Шаблоны и wiki — такие же версионированные артефакты, как и остальные:
проходят agent review и HITL-приёмку до того, как цех начнёт работу по ним.

Правило распространяется и на **конфигурацию цеха** (решение автора, 08.07.2026):
графы, конфиги узлов, реестр моделей и инструменты цеха — часть принятого пакета;
их правка = новая версия пакета → запись в CHANGELOG цеха и повторная HITL-приёмка.

Правило распространяется и на **спеки продуктов** `configs/products/` (решение
автора, 08.07.2026): product.json описывает состав целевого продукта (FR-14) и
принимается так же — CHANGELOG в `configs/products/` + повторная приёмка при правке.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| **Артефакт** | Версионированный документ этапа (XML/YAML) со стабильными id (`FR-..`, `D-..`, `C-..`, `OP-..`) и ссылкой `derived_from` на старший артефакт |
| **Мастерская** | Узел графа: конфигурация LLM (системный промпт, wiki, MCP-tools, провайдер/модель/гиперпараметры) + инструменты (песочница, библиотеки), производящий один артефакт |
| **Цех** | Последовательность мастерских под конкретный класс задач (напр. «цех data-аналитик») |
| **Оркестратор** | FSM, управляющий переходами между мастерскими и гейтами готовности |
| **Инъектируемый узел** | Узел ревью (Agent Review / Human-in-the-loop), вставляемый после любой мастерской без изменения остального графа |
| **Модуль** | Независимо тестируемая единица целевого продукта; модули соединяются adapters |
| **Adapter** | Скрипт/инструмент, организующий взаимодействие между готовыми модулями |
| **Stage-карта** | Файл фрагментов (`@fragment NAME ... @end`), которыми рантайм наполняет универсальный каркас промпта `artifact_generator.base.md` |

## 4. Цели

1. Модульность: каждый этап — инкапсулированный независимый объект; мастерские
   можно соединять в разном порядке, не противоречащем логике зависимостей.
2. Единый IO-интерфейс между модулями — без индивидуальных преобразователей.
3. Контекстная изоляция: на узле только релевантные этапу материалы и tools.
4. Единый техстек проекта, задаваемый в начале; допускается уточнение
   per-модуль по принципу наследования, изолированно внутри модуля.
5. Адаптивные конфиги: настройки пайплайна редактируемы, переиспользуемы
   между модулями и настраиваемы под проект.
6. Human-in-the-loop как первоклассный элемент: выстроенный процесс приёмки
   артефакта (accept / комментарии / reject) в любой точке графа.

## 5. Антицели

- НЕ универсальный фреймворк «на все случаи жизни».
- НЕ мультиязычность: только Python 3.14 + зафиксированные версии библиотек.
- НЕ поддержка произвольных архитектурных паттернов: только микросервисы
  (независимые сервисы в FastAPI + Docker Compose, сервис = набор независимо
  запускаемых и тестируемых модулей).
- НЕ писать tools «на все случаи жизни» — минимальный набор под методологию.

Предмет разработки — именно она.

## 7. Функциональные требования (MoSCoW)

### 7.1. Ядро (must)

- **FR-01** Рантайм сборки промптов: `final = base + stage-карта` по include-конвенции
  `@fragment`; `{{INPUTS}}` наполняется содержимым старшего артефакта согласно
  `UPSTREAM_REF` stage-карты. Ошибка сборки (нерезолвленный `{{NAME}}`) — явный отказ.
- **FR-02** Декларативный конфиг мастерской: системный промпт (base + stage-карта),
  wiki-подборка, список tools, параметры LLM (провайдер, модель, температура,
  seed и т.д.) — один файл конфигурации на узел.
- **FR-03** FSM-оркестратор: собственный минимальный движок (без LangGraph и
  подобных — гибкость под методологию важнее готовой обвязки); граф этапов
  задаётся конфигом; переход к следующему узлу возможен только при выполнении
  гейта текущего (артефакт принят).
- **FR-04** Единый IO-контракт узлов: вход/выход — версионированные артефакты
  с `derived_from` и стабильными id; кросс-ссылки валидируются автоматически
  (каждый `via="C-.."` имеет контракт, каждый FR закрыт и т.п. — по self_check
  stage-карт).
- **FR-05** Инъектируемые узлы Agent Review: вход — domain-контекст + артефакт +
  правила ревью + tools; выход — список находок с весами и вердикт-гейт
  (PASS = нет открытых 🔴p3/🟠p2).
- **FR-06** Инъектируемые узлы Human-in-the-loop: пользователю выдаётся артефакт +
  отчёт; исходы: accept / правки (комментарии → новый цикл узла) / reject.
  Интерфейс MVP — CLI (файлы артефактов + подтверждение в терминале).
- **FR-07** Обработка `NEEDS_CLARIFICATION`: если генератор артефакта вернул вопрос
  вместо артефакта — оркестратор останавливает ветку и эскалирует в HITL.
- **FR-17** Мастерская проектирования шаблонов и wiki (подготовительный этап
  цеха, §2.2): вход — техстек и класс задач цеха; выход — шаблоны артефактов,
  stage-карты, wiki-подборки и few-shot примеры (positive/negative) в `wiki/`,
  а также конфигурация цеха (граф, узлы, реестр моделей, инструменты).
  Выход версионируется и проходит те же гейты ревью (FR-05, FR-06), что и
  остальные артефакты; мастерские основного пайплайна ссылаются на конкретную
  версию шаблонов/wiki в своём конфиге (FR-02).

### 7.2. Мастерская кодогенерации (must)

- **FR-08** Вход — готовый артефакт уровня C4 (стек, алгоритмы, шаблоны,
  positive/negative примеры); генерация кода по независимым модулям (независимость =
  каждый объект кода тестируем отдельно).
- **FR-09** К каждому модулю — тесты, проверяющие что модуль работает **ровно так**,
  как задано контрактом (включая достижимость каждой ошибки из ERRORS).
- **FR-10** Песочница: запуск кода и тестов в изолированном Docker-контейнере
  (масштабируемо и совпадает с целевой средой Docker Compose); результаты
  возвращаются агенту на цикл анализ → улучшение.

### 7.3. Приёмка (should)

- **FR-11** Тестировщик-агент: проверка пользовательских сценариев, краевых случаев,
  соответствия контрактам и ФТ/НФТ; выход — заключение о готовности модуля.
- **FR-12** Judge: агрегированный вердикт о готовности сервиса по трассировке
  требования → артефакты → код → тесты.
- **FR-13** Выходной пакет: git-репозиторий с кодом, docker compose, README/quickstart,
  frozen-зависимости, CHANGELOG, отчёт о работах.

### 7.4. Отложено (could)

- **FR-14** Adapters: инструменты сборки независимых модулей в целевой продукт.
- **FR-15** Рекурсивная декомпозиция: продукт = модуль → дочерние подмодули →
  атомарные модули (в MVP — один уровень, декомпозицию даёт артефакт domains).
- **FR-16** Оптимизация стоимости: политика выбора модели per-узел
  (дешёвая на детерминированные проекции, сильная на проектирование/ревью).

### 7.5. Wiki-база знаний (should; FR-20 — could)

- **FR-18** Wiki — структурированная база доменных знаний: верхний уровень —
  области знаний (`agents/`, `python/`, `methodology/`, `domains/`, `assets/`, …);
  обязательный `index.md` в каждой директории (точка входа и каталог области);
  перекрёстные ссылки между областями — относительные MD-ссылки + секция `related`.
  Формат — Markdown, схемы — Mermaid (текст: читается LLM-узлом и рендерится
  человеку). Wiki-страницы версионируются и принимаются по правилам FR-17;
  литеральные `{{` в страницах запрещены (ломают сборку промпта FR-01).
- **FR-19** Технологический каталог и селективный инжект: `index.md` tech-области —
  реестр доступных технологий (класс задач; статус preferred / allowed / deprecated;
  ссылка на страницу с шаблонами, документацией и good/bad примерами использования).
  Стадия `tech_selection` выбирает стек ИЗ каталога и производит артефакт
  `tech_stack.xml` (WHY-обоснования + derived_from; гейты как у всех стадий).
  Конфиг узла может ссылаться на артефакт (`wiki_refs_from`) — рантайм инжектит
  в контекст ТОЛЬКО страницы выбранных технологий (реализация Цели 4 и NFR-03);
  judge проверяет, что код не использует технологии вне принятого стека.
- **FR-20** (could) HTML-витрина wiki: детерминированный рендер Markdown+Mermaid
  в статический сайт для человека — без LLM; источником остаётся Markdown.
- **FR-21** Цех актуализации wiki (`wiki_maintainer`): агентные стадии
  `wiki_spec` (спецификация изменения: страницы, related-связи, строки индексов)
  и `wiki_pages` (file map страниц, ВКЛЮЧАЯ обновлённые index.md) — обе с
  review- и HITL-гейтами; применение к файлам — детерминированный `wiki-apply`
  без LLM: валидация путей, наложение на временную копию, полный wiki-check
  по ней (включая orphan-детектор: каждая страница упомянута в index.md),
  атомарная запись, готовые CHANGELOG-строки. Wiki — самостоятельный пакет
  со своим `wiki/CHANGELOG.md` (приёмка FR-17). Скоуп: добавление и правка
  страниц; удаление запрещено. Источник знаний — гибрид: материал во входе
  приоритетен; без материала агент пишет из знаний модели с обязательной
  пометкой `unverified` на странице и проверкой на HITL.
- **FR-22** CLI фабрики (фасад поверх подкоманд, без новых зависимостей —
  NFR-05): реестр цехов `shops` (скан `configs/*/graph.json`: стадии, гейты,
  autopilot); запуск цеха ПО ИМЕНИ — `run <цех> <вход> [--autopilot]`
  (путь к graph.json остаётся рабочим); сводный статус `status [--project X]`
  (артефакты стора с версиями, узлы/итерации из журнала); запуск без
  подкоманды — интерактивное меню (цех/действие выбором, вход текстом или
  путём); HITL-вывод — отчёты гейтов ПЕРЕД артефактом.

### 7.6. MCP-интеграция (FR-23)

Назначение: внешние агентные среды (Claude Code, Claude Desktop, другие
MCP-клиенты) управляют фабрикой через инструменты MCP-сервера. Два опорных
сценария (пользователь общается с Claude, Claude вызывает инструменты):
(а) постановка задачи фабрике — выбрать цех, запустить конвейер, пройти
HITL-гейты дистанционно, забрать результаты; (б) обогащение wiki — запрос
с материалом → цех `wiki_maintainer` → применение (частный случай (а)
с авто-apply по правилу автора).

- **FR-23** MCP-сервер фабрики: запуск `python -m workshop mcp-serve`
  (транспорт MVP — stdio; подключение в Claude Code: `claude mcp add`).
  Инструменты:

  *Фабрика и прогоны:*
  - `list_shops()` — реестр цехов: стадии, гейты, autopilot (обёртка TSK-1901);
  - `run_shop(shop, input, mode, project?)` — АСИНХРОННЫЙ запуск конвейера
    (mode: interactive | autopilot); возвращает `run_id`; одновременно
    не более одного прогона на project (повтор → ошибка RUN_IN_PROGRESS);
  - `run_status(run_id)` — состояние: running(узел, итерация) |
    awaiting_decision | awaiting_answer | done(принятые артефакты) |
    failed(код, причина);
  - `get_pending_interaction(run_id)` — содержимое ожидающего гейта:
    отчёты гейтов + артефакт (в порядке FR-22) либо вопрос clarification;
  - `submit_decision(run_id, decision)` — accept | revise(comments) |
    reject(reason) | answer(text); решение доставляется прогону
    (HITL-Protocol M-08 поверх очереди; прогон живёт в фоновом потоке);
  - `list_artifacts(project)`, `get_artifact(project, name, version?)` —
    чтение стора; `project_status(project)` (TSK-1902);
  - `verify_acceptance(target)` — сверка приёмки FR-17.

  *Wiki:*
  - `wiki_update(request, material?)` — прогон цеха `wiki_maintainer`
    (материал обязателен для verified-страниц — FR-21); при успехе
    автоматически `wiki-apply` + запись в `wiki/CHANGELOG.md`
    (правило автора от 09.07.2026); ответ — применённые страницы;
  - `wiki_read(ref)` — страница или директория wiki (TSK-1601);
  - `wiki_check()` — механическая проверка wiki (индексы/ссылки/сироты).

  *Границы:*
  - Секреты (.env, ключи LLM-провайдера) живут на стороне сервера
    и клиенту не выдаются ни при каких вызовах.
  - Аргументы инструментов приходят от внешней LLM — недоверенный ввод:
    имена цехов/проектов/страниц валидируются реестрами (не путями),
    произвольные пути файловой системы в инструменты не принимаются.
  - Ошибки — кодами Result фабрики (текст без трейсбеков).
  - Инструменты описываются по методологии прожарки (TRIGGER/SKIP,
    негативные случаи) — wiki agents/prompts применима к самому серверу.

## 8. Нефункциональные требования

- **NFR-01 (методология)** Артефакты — источник истины: код всегда следствие
  артефактов; изменение кода без изменения артефакта — нарушение процесса.
- **NFR-02 (трассируемость)** Любая строка целевого кода трассируется через
  id-цепочку до FR; трассировочные таблицы — обязательная часть выхода мастерской.
- **NFR-03 (изоляция контекста)** В контекст узла не попадает ничего сверх его
  конфига (проверяемо: дамп собранного промпта на каждом запуске).
- **NFR-04 (воспроизводимость)** Прогон узла логируется целиком: собранный промпт,
  входной артефакт, параметры LLM, ответ; повторный запуск воспроизводим по логу.
- **NFR-05 (простота)** Свой минимальный код вместо тяжёлых фреймворков;
  критерий — «можно прочитать целиком за вечер». Риск «закопаться» признан
  главным (см. §11).

## 9. MVP и критерии приёмки

**MVP = «цех data-аналитик»** (document-desing.md §3.1, §3.3): вход — путь к CSV +
постановка задачи; конвейер: подготовительный этап (шаблоны + wiki, §2.2) →
постановщик задачи → приёмщик ТЗ → HITL → исполнитель (код + тесты + песочница) →
Judge → HITL-приёмка.

Критерии приёмки MVP:

1. Конвейер собирается из конфигов без правки кода фреймворка (FR-02, FR-03).
2. На демо-датасете цех проходит от запроса до работающего кода с тестами;
   все гейты ревью реально срабатывают (искусственно испорченный артефакт
   не проходит дальше).
3. `text_searcher/` воспроизводится фреймворком как второй сценарий:
   цепочка requirements → domains → contracts → openapi генерируется
   мастерскими и совпадает по структуре с golden-эталоном.
4. Логи прогонов позволяют восстановить, из чего был собран каждый промпт (NFR-03/04).
5. Шаблоны и wiki цеха произведены этапом §2.2 (FR-17), приняты через гейты ревью,
   и мастерские конвейера ссылаются на их конкретную версию — ручной подкладки
   материалов «мимо процесса» нет.

## 10. Принятые решения (автор, 08.07.2026)

1. **Канонический пайплайн артефактов** — вариант из prompts, дополненный C4-этапом:
   `requirements → domains → contracts → openapi → architecture / developmentplan (C4)`.
   GRACE-этапы вливаются в этот пайплайн (см. §2.1): основная задача — проектировать
   поэтапно и разделять бизнес-логику, архитектуру и техстек реализации,
   в исходном GRACE эти слои смешаны.
2. **Движок оркестратора** — собственный минимальный FSM: гибче под текущую
   постановку, чем LangGraph / Agent SDK (зафиксировано в FR-03).
3. **Песочница** — Docker: масштабируемее venv и совпадает с целевой средой (FR-10).
4. **Антицель про прототип** — подтверждена опечатка в document-desing.md §1.2:
   протестировать на простом приложении **планируется** (см. §9 MVP).
5. **Формат артефактов** — XML как норма; допустим HTML там, где он функциональнее
   (схемы, визуальные представления); YAML — для протокол-проекций (openapi).
6. **HITL-интерфейс MVP** — CLI (FR-06).
7. **Этап проектирования шаблонов и wiki** — добавлен в пайплайн как
   подготовительный этап цеха (§2.2, FR-17).
8. **Adapters (FR-14)** — уровень продукта: продукт = несколько независимо
   разработанных сервисов-пакетов; adapter — детерминированная compose-сборка
   (общий docker-compose, связи и env между сервисами) по декларативной спеке
   product.json (решение автора, 08.07.2026).
9. **Рекурсивная декомпозиция (FR-15)** — детерминированный декомпозитор по
   принятому domains.xml: каждый домен → дочерний проект (входной материал =
   FR-подмножество + NFR + домен + его интерфейсы из relationships), продуктовая
   спека — черновиком из рёбер доменов; дочерние пайплайны — обычные прогоны цеха
   с переопределением project; один уровень вложенности (решение автора, 08.07.2026).
10. **Политика выбора модели (FR-16)** — декларативная, в реестре моделей:
   `policy.by_class` (класс задачи узла → профиль) + `policy.default`; узел несёт
   `task_class`; приоритет источников: inline llm > llm_profile > политика.
   Динамическая эскалация (cheap → strong при провале гейта) сознательно не
   реализована — не запрошена (решение автора, 08.07.2026).
11. **Формат wiki (FR-18)** — Markdown + Mermaid как источник: HTML-разметка в
   контексте узла интерферирует с XML-зонами промптов и тратит токены; HTML —
   генерируемая витрина для человека (FR-20) (решение автора, 09.07.2026).
12. **Структура wiki (FR-18)** — верхний уровень = области знаний: `agents/`
   (промпты, инструменты агентов), `python/` (технологии экосистемы: pandas,
   fastapi, …), `methodology/` (GRACE; примеры стадий — `methodology/examples/`),
   `domains/` (предметные знания), `assets/` (изображения витрины)
   (решение автора, 09.07.2026).
13. **Цех актуализации wiki (FR-21)** — мост «артефакт → файлы» через file map
   + детерминированный applier (в духе packager: файлы — следствие принятых
   артефактов); собственный `wiki/CHANGELOG.md`; скоуп MVP — добавление и
   правка без удаления; источник знаний — гибрид с пометкой `unverified`
   для неподтверждённого материала (решение автора, 09.07.2026).
14. **CLI фабрики (FR-22)** — фасад + интерактивное меню на stdlib, без
   TUI-библиотек (rich/textual отклонены по NFR-05); имя цеха = имя
   директории `configs/<цех>/` (решение автора, 09.07.2026).
15. **MCP-сервер (FR-23)** — официальный python SDK `mcp` (обоснованное
   отступление от NFR-05: реализация протокола вручную дороже и хрупче
   зависимости); транспорт MVP — stdio, HTTP — после приёмки; интерактивность
   HITL — асинхронная пара `get_pending_interaction`/`submit_decision`
   (прогон в фоновом потоке, HITL-Protocol M-08 поверх очереди — оркестратор
   не меняется); ожидание решения без таймаута (прогон живёт, пока клиент
   не решит или сервер не остановлен) (предложение на приёмку, 09.07.2026).
