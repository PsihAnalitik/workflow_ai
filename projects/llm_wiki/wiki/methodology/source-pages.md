# wiki: вербатим-исходники (v1)

> ⚠ unverified: написано из знаний модели без внешнего материала —
> проверь факты при приёмке.

Механизм сохранения полного исходного текста материала в wiki рядом
с пересказом. Вербатим-копия **никогда не проходит через LLM** —
материализуется детерминированно из артефакта `input.xml`.

## Проблема

До v9 цеха `wiki_maintainer` исходный текст жил только в артефактах
фабрики (`input.xml`, `wiki_spec.xml/<source_request>`), а в wiki
попадал лишь сжатый пересказ. Пользователь не мог прочитать полный
исходник из витрины — только из цепочки артефактов.

## Решение (v9)

Разделение ответственности между узлами конвейера:

### wiki_spec

При наличии материала в запросе объявляет в спеке тег:

```xml
<source_page path="<страница>.source.md" for="<страница>.md"/>
```

Материал дублируется вербатим в `<source_request>` спеки — это
контрактное требование промпта, проверяемое ревьюером.

### Правило W6 ревьюера

Проверяет парность: каждый `<source_page>` обязан иметь атрибут `for`,
указывающий на существующую страницу в той же спеке, и наоборот —
если есть страница с материалом, должен быть `<source_page>`.

### wiki_pages

В пересказ страницы ставит строку:

```
Исходник: [полный текст](<страница>.source.md)
```

### wiki-apply

Материализует source-файл **детерминированно** — копирует содержимое
`<source_request>` из артефакта `wiki_spec.xml` напрямую в файл,
минуя LLM. Это решает проблему обрыва длинных генераций у DeepSeek
(лимит ~16384 токенов).

## Ограничения

- Вербатим-копия силами LLM ненадёжна — модель может сократить или
  исказить текст; поэтому копия делается кодом wiki-apply.
- Правки `workshop/*.py` требуют рестарта MCP-сервера.
