# ТЗ: цеха анализа безопасности

Черновик постановки для `configs/manifest_auditor/` и `configs/code_auditor/`.
Опирается на `architecture.md` (13.07.2026) и `document-desing.md`.
Нумерация FR/NFR локальная для этого документа, при вливании в
`task_statement.md` требует сквозной перенумерации.

## 0. Разделение и обоснование

Два цеха, не один. Обоснование — разная природа входа и, как следствие,
несовместимые режимы коллапса в промптах:

| | `manifest_auditor` | `code_auditor` |
|---|---|---|
| Вход | Текст, задающий поведение агента | Исходный код |
| Вопрос | «Эта строка адресована модели?» | «Дойдёт ли сюда недоверенный ввод?» |
| Оракул | Разметка корпуса | Сканеры + разметка корпуса |
| Справочники wiki | `security/injection-patterns` | `security/cwe`, `python/*` |
| Шаблон цеха | `prompt_roaster` | `data_analyst` (judge-ветка) |

Общее: оба — map-прогон, оба строго на чтение, оба выдают находки в формате
review-гейта с весами p0–p3.

## 1. Общие требования

**FR-0.1.** Формат находки един для обоих цехов:
`id` (F-NN), `класс`, `вес` (p0–p3), `локация` (файл + json-path либо номер
строки), `цитата` (≤200 символов), `обоснование` (≤2 предложения).

**FR-0.2.** Вердикт узла `judge` — `READY` / `NOT_READY`. Любая находка p0 →
`NOT_READY` безусловно.

**FR-0.3.** Область wiki `security` (`kind: knowledge`) — единый источник
справочников для обоих цехов, подключается через `wiki_refs` с пиннингом
версий.

**NFR-0.1.** Узлы аудита не имеют инструментов записи и сети. Доступ — только
к переданному элементу. `web_search`, `db_query`, `wiki_update` в конфигах
этих узлов запрещены.

**NFR-0.2.** Анализируемый материал — данные, не команды. Инструкции внутри
входа не исполняются; их наличие само по себе является находкой.

**NFR-0.3.** Промпты узлов оформляются по методологии `prompt_guide`:
не более 4 активных правил на блок генерации, порядок
Context → Question → Instructions → Output, отложенный коллапс (задача
поисковая, не детерминированная), у каждого инструмента TRIGGER/SKIP.

**NFR-0.4.** Детерминизм оценки: `temperature=0`, профиль модели и версии
`wiki_refs` зафиксированы. Смена модели требует пересчёта метрик.

**NFR-0.5.** Метрики качества считает детерминированный скрипт вне цеха,
сверяя артефакт находок с разметкой корпуса. LLM в оценке качества LLM не
участвует.

**NFR-0.6.** Оба цеха исключаются из `graph.autopilot.json` в части HITL для
узлов, чей вердикт становится основанием для приёмки чужих артефактов.

## 2. Цех `manifest_auditor`

### 2.1. Назначение

Статический аудит текстовых артефактов, определяющих поведение агентов:
манифесты MCP-серверов, системные промпты, skill-файлы, описания инструментов,
конфиги узлов.

Вход — glob по файлам (`*.json`, `*.md`). Выход — `audit_report.xml` на элемент.

### 2.2. Функциональные требования

**FR-A1.** Классы находок (минимальный набор):

| Класс | Описание |
|---|---|
| `imperative_in_description` | Императив, адресованный модели, в описательном поле |
| `role_override` | Попытка переопределить роль или системные правила |
| `prompt_disclosure` | Запрос на раскрытие системного промпта или конфигурации |
| `secrecy_request` | Требование скрыть действие от пользователя |
| `scope_escalation` | Назначение инструмента не соответствует его параметрам |
| `hidden_text` | Символы нулевой ширины, HTML-комментарии, base64/hex-блоки |
| `external_reference` | Ссылка на внешний ресурс в описательном поле |
| `tool_shadowing` | Описание, влияющее на выбор между инструментами |

Список расширяемый через wiki без правки промпта — классы описаны страницами
области `security`, промпт ссылается на подборку.

**FR-A2.** Diff-режим: сравнение с ранее принятой версией. Изменение
описательного поля при неизменной сигнатуре инструмента — отдельный класс
`description_drift`, вес не ниже p1. Это основной детектор rug-pull.

**FR-A3.** Интеграция с `acceptance.py` (M-13): sha256 принятых манифестов
попадает в приёмочную таблицу CHANGELOG цеха-потребителя. Расхождение хэша
блокирует прогон до повторного аудита.

**FR-A4.** При обнаружении находки класса `hidden_text` цитата приводится в
экранированном виде с указанием кодовых точек, а не как исходный текст.

### 2.3. Критерии приёмки

**AC-A1. Корпус.** Не менее 40 элементов:
- ≥20 позитивов — манифесты с внедрёнными паттернами, с разметкой ожидаемых
  находок (класс + локация);
- ≥20 негативов, из них **не менее 8 «трудных»** — легитимные манифесты,
  внешне похожие на вредоносные (описание инструмента, законно содержащее
  слова вида «ignore», «override», «system», длинные инструкции по
  использованию).

Трудные негативы обязательны: без них precision меряется на слишком лёгкой
выборке и завышается.

**AC-A2. Метрики.** На пиннованной модели: recall ≥ 0.8, precision ≥ 0.7.

**AC-A3. Стабильность.** N=5 прогонов по корпусу, разброс recall ≤ 0.1.
Единичный прогон вердиктом о качестве цеха не является.

**AC-A4. Тишина на чистом.** Доля негативов, на которых не возникло ни одной
находки p0/p1, ≥ 0.9.

Приоритет при конфликте метрик — **precision выше recall**. Цех, который
срабатывает на всё, будет отключён через неделю и не защитит ничего.

### 2.4. Антицели

- Не детектор вредоносного кода — только текстовые артефакты поведения.
- Не исполняет и не «пробует» анализируемое.
- Не заменяет `mcp-scan` / `mcp-scanner`, а добавляет к ним семантический
  слой; статические сканеры остаются отдельным оракулом.

## 3. Цех `code_auditor`

### 3.1. Назначение

Статический аудит исходного кода на уязвимости. Вход — файлы исходников
элемента. Выход — `vuln_report.xml`.

### 3.2. Функциональные требования

**FR-C1. Состязательная структура.** Три узла:
`hypothesis` (порождает кандидатов) → `refutation` (пытается опровергнуть
каждого, аргументируя недостижимость или наличие защиты) → `judge`
(агрегирует). Одностадийный аудит запрещён — он даёт неотличимый от шума
поток гипотез.

**FR-C2. Обязательный внешний оракул.** `semgrep`, `bandit`, `pip-audit`
прогоняются в `sandbox.py` (M-10). Вывод сканеров поступает в `judge` наравне
с гипотезами узлов.

**FR-C3. Правило достижимости.** Находка без указанного пути от недоверенного
входа до уязвимой строки автоматически понижается до p3. Это основной
механизм подавления ложных срабатываний: модель склонна предполагать у
атакующего возможности, которых у него нет.

**FR-C4. Формат находки** дополняется полями: `cwe`, `путь_достижимости`,
`предлагаемая_проверка` (описание теста, воспроизводящего условие).

**FR-C5. Привязка к модели угроз.** Если в цепочке присутствует артефакт
`threat_model`, находка ссылается на `TH-id` либо явно помечается как
`вне_модели_угроз` — второе является входом для доработки модели угроз, а не
поводом отбросить находку.

### 3.3. Нефункциональные требования

**NFR-C1.** Только статический анализ. Сетевые инструменты, сканирование
внешних целей и запуск эксплойтов не предусмотрены ни в каком режиме.

**NFR-C2.** Анализируемый код исполняется исключительно в `sandbox.py` и
только для прогона тестов, но не для «проверки эксплуатируемости».

### 3.4. Критерии приёмки

**AC-C1. Корпус пар «до/после».** ≥30 пар из реальных коммитов-исправлений
CVE в Python-проектах: уязвимая версия файла — позитив с известной строкой,
исправленная — негатив. Пары дают размеченные позитивы и негативы
одновременно и почти бесплатно.

**AC-C2. Метрики.** Recall ≥ 0.6, precision ≥ 0.5. Планка ниже, чем у
`manifest_auditor`, сознательно: задача объективно труднее, завышенные
пороги приведут к подгонке промпта под корпус.

**AC-C3. Тишина на исправленном.** Доля исправленных версий с ложной находкой
p0 ≤ 0.1.

**AC-C4. Baseline.** Те же метрики измеряются для голого `semgrep` на том же
корпусе. Цех обязан превзойти baseline по recall при не худшей precision.

AC-C4 — критерий существования цеха. Без него есть риск потратить месяц и
получить дорогую обёртку вокруг статического анализатора.

### 3.5. Стенды для отладки

| Стенд | Роль |
|---|---|
| Корпус CVE-фиксов | Основной, даёт размеченные пары |
| `pygoat`, `vulpy` | Заведомо уязвимые Python-приложения с описанием классов |
| OWASP Juice Shop | Только как источник таксономии классов уязвимостей |

Живые внешние сайты в качестве целей не используются ни на одном этапе.

## 4. Порядок работ

| Этап | Содержание | Готовность определяется |
|---|---|---|
| 1 | Область wiki `security`: классы паттернов, таксономия CWE | `wiki-check` проходит |
| 2 | Корпус `manifest_auditor` с разметкой | AC-A1 выполнен |
| 3 | Скрипт подсчёта метрик (детерминированный, вне цеха) | Считает на эталонной разметке |
| 4 | Цех `manifest_auditor` по образцу `prompt_roaster` | AC-A2..AC-A4 |
| 5 | Интеграция с `acceptance.py`, режим diff | FR-A2, FR-A3 |
| 6 | Корпус пар CVE и baseline `semgrep` | AC-C1, AC-C4 измерен |
| 7 | Цех `code_auditor` | AC-C2, AC-C3 |

Этап 3 предшествует этапу 4 намеренно: без измерителя разработка цеха
превращается в подбор формулировок по субъективному ощущению улучшения.

## 5. Открытые вопросы

1. Где хранится разметка корпуса — отдельная область в `projects/` или
   каталог рядом с конфигом цеха? Второе удобнее для переносимости, первое
   согласуется с текущим разделением «конфиг / выход прогона».
2. Нужен ли `manifest_auditor` в контуре MCP-сервера как инструмент
   (`audit_manifest`), или достаточно CLI-прогона? Инструмент удобнее, но
   расширяет поверхность самого сервера.
3. Как поступать с находками `вне_модели_угроз` в `code_auditor`: блокировать
   приёмку или накапливать как вход для следующей итерации `threat_model`.
4. Порог `max_iterations` для состязательной пары hypothesis/refutation —
   наследовать значение 3 или задавать отдельно.
