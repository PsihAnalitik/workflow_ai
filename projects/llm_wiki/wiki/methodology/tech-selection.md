# wiki: стадия tech_selection (v1)

Стадия, которая выбирает технологический стек из wiki-каталога и делает
селективный инжект страниц выбранной технологии в контекст downstream-стадий.
Реализована согласно FR-19.

## Место в графе

Стадия встраивается после сбора требований, перед проектированием:

```
contracts → tech_selection ← openapi
               ↓
tech_selection → c4 → executor
```

Upstream: способности из контрактов + протокол openapi — ровно то, из чего
выводится класс задач и необходимый стек.

## Артефакт: tech_stack.xml

Модель на стадии `tech_selection` выдаёт артефакт с выбранными технологиями.
Формат: перечень технологий, каждая — дословно из каталога wiki (имя директории
в `python/`), с WHY-привязкой к операциям контрактов. Пример из живого прогона
(microservice): модель выбрала `python/fastapi`, WHY привязан к операциям
OP-exact-search, OP-lemmatize.

## Селективный инжект

Принятый `tech_stack.xml` передаётся downstream-стадиям через `wiki_refs_from`:

- C4 получает `tech_stack` в upstream — проектирует в пределах стека.
- Executor получает в контекст ровно страницы выбранной технологии
  (например, `fastapi/index.md` + `testing.md`), ничего лишнего.

Механика инжекта — M-16 `wiki_loader`: резолвит ссылки (директория → index.md),
собирает бандл с дедупликацией и лимитом (`WIKI_BUNDLE_TOO_LARGE` вместо
тихого переполнения), проверяет перекрёстные MD-ссылки и отсутствие двойных
фигурных скобок.

## Judge-гейт

Правило: «код в пределах стека». Judge на стадии executor проверяет, что
сгенерированный код использует только технологии из принятого `tech_stack.xml`.
Выход за пределы стека → NOT_READY с указанием нарушения.

## Техкаталог в index.md

Каждая tech-область (например, `python/`) содержит в своём `index.md` реестр:
`технология → класс задач → статус (preferred/allowed/deprecated) → ссылка`.
Это позволяет модели на стадии `tech_selection` принять информированное решение.
