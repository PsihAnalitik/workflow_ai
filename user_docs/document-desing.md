# 1. Проблематика

Claude Code, Codex, Cursor и прочие AI фреймворки предоставляют готовый набор инструментов для работы LLM моделей с окружением: 
    - skills
    - hooks
    - system instructions

Но все они носят больше "рекомендательный" характер, чем декларативный и не дают полноценную возможность кастомизации агентов в рамках репозитория.
Отдельная сложность возникает при настройке автономного пайплайна агентской системы, поскольку это требует оптимизации расхода токенов, выбор оптимальной модели
с точки зрения когнитивных способностей для решения задачи и стоимости затрат инференса (как правило API)

Также нет возможности контролировать доступные инструменты и системные надстройки для агентов -> хардкод проверки в рамках методологии при переходе между этапами.

## 1.1. Цели

В рамках текущего проекта предлагается сформировать "виртуальную среду" для LLM, которая:
    - представляет собой этапы разработки приложения
    - модульная: каждый этап представляет собой инкапсулированный независимый объект
    - между модулями единый интерфейс обмена данными: можно конфигурировать, подключать разные модули друг к другу без дополнительного преобразования IO адаптеров
    - есть единый технологический стек, который задается в начале проекта и должен использоваться в рамках решения конкретных атомарных задач
    - технологический стек может уточняться под конкретный модуль [в рамках методологии наследования, но должен быть изолирован в рамках модуля]
    - адативные конфигурационные файлы: настройки агентского пайплайна могут быть редактируемыми, переиспользуемыми между модулями и настраиваемыми под конкретный проект;

## 1.2. Антицели:

В рамках текущей реализации не планируется:
    - разрабатывать "универсальный" фреймворк на все случаи жизни
    - протестировать на конкретном простом с точки зрения разработки пользовательском приложении
    - адаптировать под все ЯП: в рамках текущей реализации используется Python3.14 с соответствующим набором версий библиотек и документации.
    - разрабатывать конфиги и спеки под разные архитектурные паттерны: автор исповедует философию микросервисной архитектуры с разработкой независимых сервисов, обернутых
      в FastAPI и Docker compose, сервис представляет собой набор независимых модулей, которых можно по отдельности запускать и тестировать.
    - писать Tools агентов на все случаи жизни: тестирование, запуск, отладка и так далее. 


## 1.3. Риски и ограничения

    - нет ресурсов, знания, команды для полноценного продуманного фреймворка
    - если всё делать по уму - то велик риск закопаться
    - использоваться ли AI на этапе проектирования и разработки? Думаю не стоит, иначе это будет еще один не управляемый фреймворк

# 3. Решение

Представим разработку продукта следующим образом:
    1. Разработка состоит из этапов: описание бизнес-требований; проектирование; разработка прототипа; тестирование; ввод в эксплуатацию / production
    2. В Agile методологии часто фигурирует подход "каждый этап должна создаваться рабочая версия продукта"
    3. В waterfall подходе есть набор "универсальных" шагов, которые проводятся на нескольких или почти всех этапах: согласование / review; тестирование; версионирование;
    4.

Идея:

сделать что-то вроде отдельных модулей с:
    0. инструменты: набор библиотек, утилит, алгоритмов, используемых в проекте. Возможно с документацией, few shots примерами.
    1. input: входящие материалы для формирования артефакта
    2. Human in the loop: выстроенный процесс приемки артефакта пользователем, агент готовит набор отчетных документов и юзер может аксептнуть, дать правки или отклонить с замечаниями на новый цикл разработки.
    3. мастерская: генерация продукта "по ТЗ" + тестирование
    4. Review: оценка реализованного продукта на требования ТЗ, эффективность использованных алгоритмов и т.д.
    5. тестировщик: проверка пользовательских сценариев, краевых / пограничных случаев -> формриование заключения о готовности модуля.
    6. output: docker compose, документация по коду + отчет о проделанной работе, сам код в виде репозитория git с quickstart, README.md, frozen зависимостями и т.д.

Каждый модуль генерируется из этих блоков, причем блоки можно ставить последовательно в "любом порядке" не противоречащим логике: чтобы начать писать код нужно ТЗ условно. Чтобы тестировать нужен продукт и тд
Human in the loop можно тыкать в разные части модуля, также как reviewer и тестировщик. 

А теперь посмотрим с другой стороны:
есть задача от пользователя собрать какое-то приложение, например. "Какой-то продукт". Он представляет собой один большой модуль.
Но в рамках формирования input материалов его можно представить в виде набора дочерних связанных между собой "подмодулей". 

И так до атомарного модуля, который представляет собой независимый от других модулей элемент, закрывающий некоторую часть исходного функционала продукта.

И вишенка на торте: поскольку модули независимы, их можно независимо запускать, тестировать, а далее объединять через "adapters".
adapters - набор инструментов / скриптов, которые организуют взаимодействие между модулями. 

Помимо модуля есть еще один отдельный элемент: оркестратор. Это агент который организует работу модулей, контролирует степень их готовности,

Нужно думать в двух плоскостях:
    - что делаем?
    - как делаем?

Что делаем: 
    - system design по этапам
    - реализация модулей по заданной методологии.


Как делаем:
    - skills
    - набор wiki документации к библиотекам, с шаблонами реализации, few shots примерами хорошего и плохого использования.
    - MCP tools: набор инструментов доступных агенту на заданном этапе
    - системные инструкции


## 3.1. Область реализации

В качестве прототипа выбран сценарий анализа табличных данных с использованием pandas, numpy, stats, scikit-learn библиотек на python.

Сценарий: агенту на вход подается csv датасет / путь к csv датасету + постановка задачи.

1. Агент читает датасет, проверяет что путь релевантный файл есть, изучает его.

1.2. Далее на основе изученной информации агент формирует описание таблицы:
    - доступные колонки
    - количество данных (полнота / наличие пропусков, типы данных)
    - индекс: тип / дискретность и т.д.
    - особенности датасета: 

2. RequirementAnalysis
    - Формализация пользовательского запроса
    - формирование пользовательских сценариев: как пользователь будет использовать сформированное решение?  [если речь про аналитику, то как результаты будет юзер использовать в работе]
    - полнота требований, наличие неопределенности или скрытых допущений -> явная формализация.
    - Сопоставление бизнес-части с фактическими данными в таблице 
    - Формирование ТЗ на разработку
    - В рамках целевого результата разбить целевую "систему" на независимые модули: классы; функции; скрипты.
    - описать IO потоки между модулями: в каком формате должны передаваться данные между модулями. Кто является точкой входа / выхода для пользователя?

2.2. RequirementAnalysis Reviewer:
Проверка агента по чек-листу:
    - соответствие запроса пользователя сформированным пользовательским сценариям
    - соответствие ТЗ исходному запросу и пользовательским сценариям
    - соответствие модулей ТЗ и насколько "необходимо и достаточное количество модулей" сформировано: проверка по методологиям разработки DRY & архитектурному микросервисному подходу

2.3. Human in the loop

3. Technology
    - Какой дефолтный стек задан?
    - Что из этого подходит 
    - Какие из дефолтных алгоритмов можно переиспользовать в проекте? 
    - Чего не хватает / не покрывает текущий стек? 
    - предлагаемые варианты библиотек и алгоритмов для тех модулей, которые не покрываются текущим стеком (с обоснованиями и аргументами в формате: за и против)

3.2. Reviewer:
    
3.3. Human in the loop

4. DevelopmentPlan

4.1. На уровне взаимодействия между модулями сформировать архитектуру: 
    - как будет реализована оркестрация модулей и передача данных между модулями
    - e2e тесты
    - golden тесты

4.2. SubPlan
    - для каждого модуля формируется свой DevelopmentPlan_ со ссылкой на исходный DevelopmentPlan
    - детализация до атомарных задач в рамках разработки модуля: последовательная цепочка A->B->C
    - покрытие unit тестами
    - покрытие golden module тестами
    - аппаратные риски: затраты по памяти, сложность алгоритмов и работы модуля

4.3. Review:
    - SubPlan
    - DevelopmentPlan

4.4. Human in the loop

5. Генерация кода 
    - модули
    - тесты к модулям
    - тесты к системе

6. Code Review

7. Judge: оценка проведенных работ на соответствие ТЗ

8. актуализация CHANGELOG -> выполненных работ


## 3.2. Архитектура

мастерская агента состоит из следующих частей:
1. конфигурация: сюда входит всё что относится к LLM: 
    - системные инструкции
    - MCP инструменты
    - WIKI
    - параметры LLM: провайдер, API key, name, гиперпараметры (температура, сид, топ_k и т.д.)

2. инструменты:
    - виртуальная среда
    - библиотеки

3. Оркестратор: это FINITE STATE MACHINE для налаживания взаимодействия между мастерскими.

## 3.3. Цех data-аналитик

1. Мастерская: постановщик задачи
2. Мастерская: приемщик ТЗ
3. Human in the loop: обратная связь по задаче
4. Мастерская: исполнитель
5. Мастерская: Judge
6. Human in the loop: приемка результата.
