# wiki: методология артефактной цепочки (v1)

Общая подборка для всех узлов цеха «микросервис». Артефакт каждой стадии — следствие
старшего артефакта; код в конце цепочки — следствие артефактов, никогда наоборот.

## Цепочка и слои

```
requirements → domains → contracts → openapi → architecture/developmentplan (C4)
   STRICT       STRICT      STRICT     PROJECTION        PROJECTION
```

- **STRICT** — тест замены стека: «заменю весь технологический стек — артефакт не изменится».
  Имена библиотек, СУБД, протоколов, форматов хранения запрещены. Разрешены способности,
  метрики (p95, мс, RSS), бизнес-ограничения.
- **PROJECTION** — проекция контракта на конкретный протокол/стек; тех-специфика разрешена,
  но каждый выбор с альтернативой несёт WHY-комментарий.

## id-схемы и трассировка

- `FR-NN` — функциональные требования; `NFR-NN` — нефункциональные;
  `D-NN` — домены; `C-xxx` — контракты; `OP-xxx` — операции.
- Каждый артефакт несёт `derived_from="<старший>@<версия>"` в корне.
- Ссылка допустима только на существующий id старшего документа.
  Исключение — ссылка «вперёд»: ребро домена `via="C-.."` резервирует id будущего
  контракта; на следующей стадии контракт обязан получить ровно этот id.
- Покрытие: каждый FR закрыт ≥1 доменом; каждый домен — ≥1 контрактом;
  каждая операция несёт `<covers>FR-..</covers>`.

## Ошибки — варианты возврата, не исключения

- В контрактах `ERRORS` — это варианты Result-возврата операции.
- Каждая ошибка должна быть **достижима конкретным входом** (мысленный тест:
  подбери вход на каждую ошибку). Недостижимая ошибка — дефект контракта:
  удали её или поправь входы.
- «INTERNAL_ERROR / что-то пошло не так» — не ошибка контракта: она не достижима
  определённым входом и не даёт вызывающему ветвления.

## WHY-комментарии

- Ставятся ТОЛЬКО там, где у решения была альтернатива, и объясняют ВЫБОР
  («почему так, а не иначе»), не действие.
- Тривиальная строка без WHY. Артефакт, где WHY на каждой строке, — дефект.

## Границы ответственности

- Один домен — одна ответственность, один единый язык (ubiquitous language).
- Одна операция — один чёткий контракт: INPUTS / OUTPUTS / ERRORS, без скрытых
  побочных эффектов.
- Абстрактный словарь типов STRICT-слоя: string, int, bool, float,
  list<T>, optional<T>, enum{...}, record.
