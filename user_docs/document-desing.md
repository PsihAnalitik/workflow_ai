# Концепция и дизайн-решения Agent Workshop

Актуальность: 13.07.2026. Документ отвечает на «почему продукт устроен так»;
«что требуется» — `task_statement.md`, «как устроено» — `architecture.md`.
Исходный мозговой штурм (июнь 2026) сохранён в git-истории этого файла.

## 1. Проблематика

AI-инструменты кодинга (Claude Code, Codex, Cursor) кастомизируются только
«рекомендательно» — skills, hooks, system instructions. Из этого следуют
четыре системных ограничения:

- контекст и инструменты агента нельзя декларативно ограничить под этап
  разработки — всё сваливается в общий контекст, LLM генерирует код из
  размытого belief state;
- гейты «этап не пройден — дальше нельзя» не выражаются штатно;
- нет выбора модели под когнитивную сложность этапа (стоимость инференса);
- автономный пайплайн «требования → архитектура → код → приёмка» не
  переиспользуется между проектами.

## 2. Идея

Разработка = **граф состояний**. Узел графа — **мастерская**: агент, которому
подаётся только релевантное этапу (промпт, wiki-подборка, инструменты) и
который производит один версионированный **артефакт** с трассировкой к
старшему (`derived_from`). Между узлами — единый интерфейс обмена
артефактами. В любую точку графа инъектируются узлы ревью — агентского и
человеческого. Оркестратор — детерминированный FSM, LLM в управлении
переходами не участвует.

Следствие для целевого кода: код — всегда последний артефакт цепочки,
следствие принятых старших артефактов, никогда наоборот (NFR-01).

## 3. Истоки

Методология выросла из **GRACE** (артефактная цепочка
RequirementAnalysis → Technology → DevelopmentPlan → Code → Review):
<https://m.vk.com/@turboplanner-grace-freimvork-sozdaniya-koda-llm-v-bolshih-kontekstah-s-uc>.

Ключевое отличие от исходного GRACE: слои разделены. STRICT-слой
(requirements, domains, contracts) проектируется тех-агностично — артефакт
обязан переживать замену стека; PROJECTION-слой (openapi, c4) — проекция на
стек, выбранный отдельной стадией `tech_selection` из wiki-каталога
технологий. В исходном GRACE бизнес-логика, архитектура и стек смешаны.

## 4. Ключевые дизайн-решения

| Решение | Отклонённая альтернатива | Почему |
|---|---|---|
| Собственный минимальный FSM | LangGraph, Agent SDK | Гибкость под методологию важнее готовой обвязки; ядро читается целиком за вечер (NFR-05) |
| Детерминизм везде, где LLM не нужна: packager, assembler, decomposer, wiki-apply | «Агент применит сам» | Применение принятого артефакта к файлам не должно вносить недетерминизм; LLM — только там, где нужно порождение |
| Артефакты XML со стабильными id | Свободный Markdown | Валидируемые кросс-ссылки, трассируемость каждой строки кода до FR (NFR-02) |
| Wiki — Markdown + Mermaid, HTML только как витрина | HTML-страницы в контексте | HTML интерферирует с XML-зонами промптов и тратит токены; Mermaid читается и LLM, и человеком |
| Контекст узла собирается только из его конфига, промпт дампится в журнал | Общая память агента | Изоляция проверяема (NFR-03), прогон воспроизводим по логу (NFR-04) |
| Review-гейт возвращает узел в работу с адресными находками (rework) | Перегенерация артефакта | Дешевле и стабильнее: правится найденное, не ломается принятое |
| Оценка кода — judge-гейт, review-гейт для codegen запрещён | Единый ревьюер на всё | Код проверяется прогоном тестов и таблицей покрытия требований, а не чтением |
| HITL — первоклассный элемент: протокол Accept/Revise/Reject | «Автономность прежде всего» | Приёмка человеком — часть методологии; autopilot — отдельный граф только для smoke |
| Конфиг цеха, шаблоны и wiki — тоже принимаемые артефакты (sha256-приёмка) | Правка конфигов «мимо процесса» | Артефакты — источник истины распространяется на саму фабрику |
| `Result` (`Ok`/`Err`) вместо исключений в бизнес-логике | try/except-поток | Явные возвраты детерминированнее для LLM-генерируемого и LLM-читаемого кода |
| MCP-сервер на официальном SDK `mcp` | Ручная реализация протокола | Обоснованное отступление от NFR-05: вручную дороже и хрупче |

## 5. Антицели (в силе)

- Не универсальный фреймворк «на все случаи жизни».
- Только Python 3.14 с зафиксированными версиями библиотек.
- Только микросервисный паттерн: FastAPI + Docker Compose, сервис — набор
  независимо запускаемых и тестируемых модулей.
- Минимальный набор tools под методологию, не «на все случаи».

## 6. Эволюция

Путь от наброска до реализации: мозговой штурм (июнь 2026, git-история этого
файла) → ТЗ v1–v6 с решениями автора (июль 2026, git-история
`task_statement.md`) → реализация ядра, шести цехов, wiki-контура и
MCP-интеграции (текущее состояние — `architecture.md`). Дальнейшие
