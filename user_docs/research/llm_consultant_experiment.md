# Эксперимент: слабая LLM-рабочая + LLM-консультант при тупике

Дата: 24.07.2026. Метод: живые прогоны на фабрике, цех `microservice`, проект
`text_searcher`, замороженный upstream (c4@v2 подаётся во все плечи одинаково,
живьём выполняется только codegen-узел `executor`). Всего 13 прогонов.

Проверяемые тезисы (из поста об оркестрации сильных/слабых моделей):
- **T1** — рутинный кодоген по готовому контракту под силу слабой модели;
  сильная модель «везде» — переплата.
- **T2** — связка «слабый рабочий + сильный консультант при тупике» ≥ по
  качеству сильной модели везде, при меньшей цене.
- **T3** — часть пользы консультанта — сброс контекста («разморозка» от
  неверной гипотезы), а не сила модели. Механистические объяснения поста
  (KV Cache, «гиперконнекции») не проверялись — паттерн тестируется независимо.

Статус: **направление подтверждено, статистикой не является** (одна задача,
малое n, недетерминированный провайдер). Решающие следующие шаги — в §6.

---

## 1. Устройство стенда

Хук консультанта в `workshop/codegen_loop.py::run_codegen`: при провале
**предпоследней** итерации и заданном `consultant_profile` — один вызов второй
модели со **свежим контекстом** (C4-контракт + текущий file map + test report,
без цепочки rework), совет вклеивается в контекст последней попытки блоком
`<consultant_advice>`. Best-effort: отказ консультанта логируется, узел не
падает. Вызов пишется в run_log как `{node}:consult`; поле `usage` (токены)
добавлено во все точки логирования.

Промпт консультанта содержит: команду тестов и docker-образ, запрет
диагностировать отсутствие пакетов вне `<sandbox_env>` (список предустановленного
— из `NodeConfig.sandbox_notes`), обязательную проверку полноты file map.

Плечи (модели через aitunnel; `max_iterations=2` в C/D — ужесточение, чтобы
провал первой итерации сразу триггерил консультанта):

| Плечо | Рабочая | Консультант | Прогонов |
|---|---|---|---|
| A (baseline, история) | deepseek-v4-pro | — | 2 |
| B | deepseek-v4-flash | — | 1 (max_iter=3) |
| C | deepseek-v4-flash | glm-5.2 | 6 |
| D | deepseek-v4-flash | deepseek-v4-flash | 7 |

Плечо D — ключевая добавка к посту: консультант **той же слабой моделью**
изолирует эффект сброса контекста от силы модели.

Стенды: `projects/text_searcher/experiments/arm{B,C,D}/` (graph, models,
executor.json, сторы rep1–6). Перезапуск плеча: одна команда
`workshop run <graph> <input> --store <rep>/artifacts --log <rep>/runs/log.jsonl --resume`.

## 2. Итоги прогонов

| Плечо | Pass | Комментарий |
|---|---|---|
| A pro (история) | 2/2 | 2 и 3 итерации из трёх |
| B flash, без консультанта | 1/1 | прошёл за 2 итерации из трёх |
| C flash + glm-5.2 | **2/6** | из них 2 провала — консультация не состоялась (см. §4) |
| D flash + flash | **6/7** | один раз прошёл вообще с первой итерации |

Разрез «совет получен / не получен» по C/D:
- совет получен → **8/11 pass** (C: 2/4, D: 6/7);
- совета нет (пустой ответ GLM) → **0/2 pass**.

## 3. T1 подтверждён: flash не хуже pro на рутинном кодогене

На идентичном c4@v2 flash прошёл за 2 итерации там, где pro потребовалось 3.
Однако flash **недетерминирован при temperature=0**: одинаковый промпт первой
итерации давал то чистый проход, то лемма-баг, то вырожденный ответ с одним
файлом из семи. Единичный прогон ничего не доказывает — только серии.

## 4. Главный сюрприз: дешёвый консультант обыграл сильного

Типовой тупик задачи — сгенерированные тесты ожидают, что pymorphy3
лемматизирует «бегу» в «бежать», а тот выбирает разбор-существительное «бег».
Это ровно «мелкая, но важная деталь» из поста — и её стабильно находили **оба**
консультанта.

Разница оказалась не в диагнозе, а в **формате совета**:
- flash-консультант: короткие директивы («исправь ожидание с "бежать" на "бег"
  в test_lemmatization.py и test_api.py»), 0.2–2.3K токенов ответа → рабочая
  модель отрабатывала дословно → 6/7;
- glm-5.2: верные, но многословные разборы на 2–6K токенов → рабочий flash за
  единственную оставшуюся попытку чинил часть и не дочищал хвост (rep4 — не
  исправил лемму, rep5 — исправил лемму, но завалил root-search) → 2/4.

Вывод в терминах T3: **свежий контекст + директивный формат дали больше, чем
сила модели консультанта**. «Сильный консультант» T2 на этой задаче пользы не
добавил и стоил дороже. Оговорка: возможен конфаундер стиля (GLM не просили
быть кратким) — см. §6.

## 5. Операционные грабли (переносимы на другие цеха)

1. **Reasoning-модели при тесном `max_tokens` отдают пустой ответ**
   («PROVIDER_ERROR: пустой ответ модели»): flash молчит при лимите ~200,
   glm-5.2 выел 8192 и молчал в 2 консультациях из 3. Лечение: консультанту
   32000 (стоит в `configs/microservice/models.json`), рабочим — ≥16384.
2. **Галлюцинация об окружении**: до добавления `<sandbox_env>` GLM
   «диагностировал» отсутствие pymorphy3, который предустановлен в образе.
   Список пакетов песочницы обязан быть в промпте консультанта
   (`NodeConfig.sandbox_notes`).
3. **Вырожденный file map**: рабочий flash может выдать один файл из семи
   (exit 5 «no tests ran»). Инструкция консультанту «сначала проверь полноту
   file map» добавлена в промпт хука.
4. Транзиентные «Connection error» aitunnel — лечатся перезапуском.

## 6. Открытые вопросы и следующие шаги

1. **Конфаундер стиля совета**: добавить в C промпт-инструкцию «только короткие
   директивы, без разбора» — отделит силу модели от формата. Дёшево, 3 прогона.
2. **Вторая задача-стенд** (другой контракт или цех `data_analyst`): проверить,
   что результат не артефакт text_searcher.
3. **Плечо B на серии**: B прогнан один раз; для честного «нужен ли консультант
   вообще при max_iter=3» нужна серия B тем же n.
4. Дизайн-вопрос: не давать ли консультанту «право» возвращать патч тестов
   напрямую (сейчас он только советует, рабочая модель может совет исполнить
   частично).
