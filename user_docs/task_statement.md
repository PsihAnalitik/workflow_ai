# Постановка задачи: «Агентская мастерская»

Фреймворк агентной разработки ПО по артефактной методологии (GRACE-подобной):
конвейер мастерских-агентов с контекстной изоляцией, управляемый
FSM-оркестратором, с обязательными точками ревью (агентского и человеческого)
между этапами.

Статус: **v7 — актуализация по факту реализации** (13.07.2026). Все
must/should-требования v6 реализованы, включая бывшие could FR-14/15/20;
сверх ТЗ добавлены материал-стор, map-драйвер и новые цеха (§6).
История версий v1–v6 — в git-истории этого файла.

Техническое устройство — `architecture.md`; концепция и обоснования —
`document-desing.md`.

---

## 1. Проблема

Существующие AI-инструменты кодинга (Claude Code, Codex, Cursor) дают только
«рекомендательные» механизмы кастомизации (skills, hooks, system instructions):

- нельзя декларативно ограничить контекст и инструменты агента на конкретном
  этапе разработки;
- нет управляемых переходов между этапами и гейтов «этап не пройден — дальше
  нельзя»;
- нет выбора модели под когнитивную сложность этапа;
- автономный пайплайн «требования → архитектура → код → тесты → приёмка»
  не переиспользуется между проектами.

## 2. Решение (как реализовано)

Разработка представлена **графом состояний**; узел — **мастерская**:
инкапсулированный LLM-агент, которому подаётся только релевантная этапу
информация (промпт, wiki-подборка, инструменты) и который производит ровно
один **артефакт** с трассировкой `derived_from`. Между узлами — единый
интерфейс версионированных артефактов. В любую точку графа инъектируются узлы
ревью: агентского (находки p0–p3 + вердикт-гейт) и человеческого
(accept / revise / reject). Оркестратор — собственный минимальный FSM.

Канонический пайплайн артефактов (цех `microservice`):

```
requirements → domains → contracts → openapi → tech_selection → c4 → код
```

STRICT-слой (requirements, domains, contracts) — тех-агностичен;
PROJECTION-слой (openapi, c4) — проекция на выбранный из wiki-каталога стек.

## 3. Глоссарий

| Термин | Значение (по реализации) |
|---|---|
| **Артефакт** | Версионированный документ этапа со стабильными id (`FR-..`, `D-..`, `C-..`, `OP-..`) и `derived_from`; version=0 — черновик до приёмки |
| **Мастерская** | Узел графа: конфиг LLM (base-промпт + stage-карта, wiki-ссылки, tools, профиль модели), один запуск = один артефакт или вопрос |
| **Цех** | Директория `configs/<имя>/`: граф мастерских под класс задач; обнаруживается сканом `graph.json` |
| **Оркестратор** | FSM `orchestrator.py`: переходы, гейты, итерационные циклы, resume |
| **Материал** | Вход цеха как чанк-стор: большой вход подаётся оглавлением + инструментами `material_search/get` |
| **Review-гейт** | LLM-ревьюер → находки с весами → PASS/FAIL; FAIL возвращает узел в работу с rework-контекстом |
| **Judge-гейт** | Только для codegen: вердикт READY/NOT_READY с таблицей покрытия, автоцикл judge→codegen |
| **HITL** | Протокол Accept/Revise/Reject + ответы на clarification; реализации: CLI и MCP-очереди |
| **Пакет / Продукт** | Пакет — детерминированная сборка кода проекта (git, frozen deps); продукт — compose из нескольких пакетов-сервисов |
| **Map-прогон** | Итерация цеха по списку элементов (файлы/таблицы), под-стор на элемент, параллельно |
| **Stage-карта** | Файл фрагментов `@fragment NAME ... @end`, наполняющих каркас base-промпта |

## 4. Цели и антицели

Цели (все достигнуты в реализации): модульность этапов; единый IO-интерфейс
(версионированные артефакты); контекстная изоляция узла (проверяемо дампом
собранного промпта); единый техстек с выбором из wiki-каталога; адаптивные
конфиги цехов; HITL как первоклассный элемент.

Антицели (в силе): не универсальный фреймворк; только Python 3.14; только
микросервисный паттерн (FastAPI + Docker Compose); минимальный набор tools.

## 6. Реализовано сверх ТЗ v6

- **Материал-стор (M-22)**: чанкование входа, TOC, лексический ретривер
  (опциональный векторный BGE-M3), инструменты `material_search/get`,
  `wiki_search/get`.
- **Map-драйвер (M-23)**: массовые прогоны цеха по файлам/таблицам,
  под-стор на элемент, параллельно до 16 воркеров.
- **Инструменты узлов**: веб-поиск (M-21, Tavily), read-only SQL (M-24,
  psycopg).
- **Новые цеха**: `llm_wiki` (вики из чатов), `prompt_roaster` (прожарка
  промптов), `table_validator` (валидация schema.yaml) — map-цеха без HITL.
- **Rework-контекст ревью**: адресная правка по находкам F-NN с якорями
  вместо перегенерации артефакта.
- **Шкала весов ревью — свойство цеха**: `GraphConfig.severity_scale`
  (`p3_high` по умолчанию | `p0_high`). Нужна цехам анализа безопасности,
  где постановка задачи задаёт обратную шкалу (`p0` блокирующий);
  глобальный переворот сломал бы гейты остальных цехов.
- **Новые цеха**: `manifest_auditor` (аудит манифестов и промптов на
  внедрение) и `code_auditor` (аудит кода, состязательная тройка
  hypothesis→refutation→judge с внешним оракулом bandit/semgrep).

## 7. Нефункциональные требования — статус

- **NFR-01 (артефакты — источник истины)** — соблюдается процессом: код цеха —
  следствие принятых артефактов; файлы wiki — следствие file map.
- **NFR-02 (трассируемость)** — id-цепочки FR/D/C/OP + `derived_from`;
  трассировочные таблицы в артефактах.
- **NFR-03 (изоляция контекста)** — в контекст узла попадает только конфиг
  узла; собранный промпт дампится в журнал.
- **NFR-04 (воспроизводимость)** — `run_log.py`: JSONL с промптом, входом,
  параметрами LLM и ответом на каждый запуск узла.
- **NFR-05 (простота)** — ядро без тяжёлых фреймворков; обоснованные
  отступления: SDK `mcp` (решение №15), pydantic для конфигов.

## 8. Критерии приёмки MVP — статус

1. Конвейер собирается из конфигов без правки ядра — **выполнено** (6 цехов
   на одном ядре).
2. Демо-прогон data_analyst от запроса до кода с тестами, гейты реально
   срабатывают — **выполнено** (`projects/sales_analysis`, включая
   rework-smoke серию).
3. Воспроизведение `text_searcher/` цехом microservice — **выполнено**
   (`projects/text_searcher`).
4. Логи позволяют восстановить сборку каждого промпта — **выполнено**
   (NFR-03/04).
5. Шаблоны и wiki цеха принимаются через гейты, узлы ссылаются на конкретную
   версию — **выполнено** (FR-17: CHANGELOG + `verify-acceptance`).

## 9. Принятые решения (сводка действующих)

1. Канонический пайплайн `requirements → domains → contracts → openapi → c4`;
   GRACE-этапы вливаются в него (разделение бизнес-логики, архитектуры, стека).
2. Собственный минимальный FSM вместо LangGraph/Agent SDK.
3. Песочница — Docker.
4. Формат артефактов — XML (HTML где функциональнее, YAML для openapi).
5. HITL-интерфейс — CLI; дистанционный HITL — через MCP-очереди.
6. Wiki — Markdown + Mermaid; HTML — только генерируемая витрина.
7. Структура wiki — области знаний: `agents/`, `python/`, `methodology/`,
   `domains/`, `assets/`.
8. Wiki-скоуп цеха: добавление и правка страниц, удаление запрещено; знания
   без материала — с пометкой `unverified`.
9. Adapters — уровень продукта: детерминированная compose-сборка по
   `product.json`.
10. Декомпозиция — детерминированная, по принятому `domains.xml`, один уровень.
11. Политика моделей — декларативная (`policy.by_class`), без динамической
    эскалации.
12. CLI — фасад + меню на stdlib, без TUI-библиотек.
13. MCP — SDK `mcp`, stdio; HTTP-транспорт — после приёмки.
